## 2. Detailed Comparison: Spec 11 vs. Official SePay Documentation

| Area | Spec 11 (`docs/spec/11-SEPAY-INTEGRATION.md`) | Official SePay Docs (Verified 2026-11-15) | Diff / Impact on Implementation |
|---|---|---|---|
| **a) Webhook Authentication Modes** | **§2.3, §5.2, §9:**<br>- Supports `SePay:Webhook:AuthMode = Hmac \| ApiKey` (Production must not be `None`).<br>- Mode `Hmac` (primary): requires `X-SePay-Timestamp` (Unix seconds, reject if `\|now - timestamp\| > 300s`) and `X-SePay-Signature` (`sha256=<hex>`). Computes HMAC-SHA256 over `"{timestamp}.{rawBody}"` using `SEPAY_WEBHOOK_SECRET` and compares in constant time.<br>- Mode `ApiKey` (fallback): checks `Authorization: Apikey <key>` in constant time.<br>- Failure → HTTP `401` `{"success": false}`, no DB writes. | **`/vi/sepay-webhooks/xac-thuc` & `docs.sepay.vn/tich-hop-webhooks.html`:**<br>- SePay **natively** supports 4 authentication modes in Step 3 (Bảo mật) of the webhook wizard (and lists 5 internal enum values in `so-sanh-voi-live.md`: `No_Authen`, `Api_Key`, `Secret_Key`, `OAuth2.0`, `HMAC_SHA256`):<br>  1. **HMAC-SHA256 (Khuyến nghị):** Native SePay mode! SePay signs `{timestamp}.{raw_body}` with the webhook's Secret Key and sends `X-SePay-Signature: sha256={hex_hash}` and `X-SePay-Timestamp: {timestamp}` (Unix seconds). Official PHP/Node/Python sample code verifies `abs(time() - timestamp) > 300` and constant-time digest comparison over raw body bytes.<br>  2. **API Key:** SePay sends header `Authorization: Apikey YOUR_API_KEY`.<br>  3. **OAuth 2.0:** SePay calls merchant token endpoint (`client_credentials` or custom JSON) and sends `Authorization: Bearer {access_token}`.<br>  4. **Không xác thực (`None`):** No auth header (test only).<br>- Note: Older SePay pages (`/vi/dia-chi-ip` §"Xác thực nguồn gọi" and `/vi/sepay-webhooks/tao-qr-va-form-thanh-toan`) still only mention `Authorization: Apikey YOUR_API_KEY` + IP allowlist + API reconciliation. | **No breaking diff — Spec 11's dual `Hmac` + `ApiKey` design is 100% aligned with SePay's native webhook capabilities:**<br>1. `HMAC-SHA256` is **not** merely a custom proxy mode; it is SePay's **native recommended mode** on both Live and Test mode (`my.sepay.vn`).<br>2. Keeping `ApiKey` (`Authorization: Apikey <key>`) as a first-class configurable mode alongside `Hmac`, combined with the proxy IP allowlist and periodic API reconciliation, guarantees compatibility if a merchant configures API Key authentication instead of HMAC.<br>3. Secret Key / API Key is shown in full **only once** upon creation in SePay Dashboard (`****xxxx` afterwards). |
| **b) Webhook JSON Payload Fields** | **§5.3, §5.6:**<br>- Parses JSON into DTO with 12 fields: `id, gateway, transactionDate, accountNumber, subAccount, code, content, transferType, description, transferAmount, accumulated, referenceCode`.<br>- `id` used as `ProviderTransactionId` (unique per provider).<br>- `transferType != "in"` → `Ignored` (`OutgoingIgnored`).<br>- Payment code extracted from `code` if present, else regex `GH\d{10}` over `content` (case-insensitive). | **`/vi/sepay-webhooks/tich-hop-webhook` & `/test-mode/bat-dau-nhanh`:**<br>- Exact same 12 JSON fields verified:<br>  - `id` (`integer`, non-null): SePay transaction ID; stable across all retries and manual replays. *(Note: in Dashboard "Gửi thử" test-send, `id` is a mock integer, typically `0`.)*<br>  - `gateway` (`string`, non-null): Bank brand name (e.g., `"Vietcombank"`, `"MBBank"`).<br>  - `transactionDate` (`string`, non-null): `"YYYY-MM-DD HH:mm:ss"` in Vietnam time (`UTC+7`).<br>  - `accountNumber` (`string`, non-null): Bank account number.<br>  - `subAccount` (`string`, nullable/empty): Matched VA or TKP code; `""` in Live docs, `"subAccount": null` in Test mode sample payload.<br>  - `code` (`string`, nullable/empty): Extracted payment code; `null` (or `""` in Test mode docs) when no configured prefix/structure matches.<br>  - `content` (`string`, non-null): Raw transfer memo from bank.<br>  - `transferType` (`string`, non-null): `"in"` or `"out"`.<br>  - `description` (`string`, nullable/empty): Full bank description (empty if unsupported by bank).<br>  - `transferAmount` (`integer`, non-null): Positive integer VND (`long`).<br>  - `accumulated` (`integer`, non-null): Balance after transaction (`0` if unsupported by bank).<br>  - `referenceCode` (`string`, nullable/empty): Bank reference code (`SB...` in Test mode). | **Minor DTO nullability & "Gửi thử" nuances to enforce in C# implementation:**<br>1. In C# `SePayWebhookPayloadDto`, declare `SubAccount`, `Code`, `Description`, and `ReferenceCode` as nullable `string?` and treat `string.IsNullOrWhiteSpace(dto.Code)` as "no code" before falling back to the `GH\d{10}` regex over `content`.<br>2. Map `id` as `long` in JSON (`ProviderTransactionId = dto.Id.ToString(CultureInfo.InvariantCulture)`).<br>3. If an admin clicks **Gửi thử** in SePay Dashboard (`id == 0` and sample `code`), it will safely record as `UnknownCode` / `WrongAccount` in `WebhookEvents` and return `200 {"success": true}` without confirming any real order. |
| **c) Webhook Response Contract** | **§5.4, §5.8:**<br>- Must return HTTP `200` (or `201`) with JSON `{"success": true}` well inside `30 s` (including for duplicates and ignored `out` transactions).<br>- Auth failure → `401` `{"success": false}`.<br>- Invalid JSON → `400`.<br>- Unexpected exception → mark `Failed`, return `500` so SePay retries. | **`/vi/sepay-webhooks/tich-hop-webhook` & `docs.sepay.vn/tich-hop-webhooks.html`:**<br>- Success requires **all 3 conditions**:<br>  1. HTTP status `200` or `201` *(note: for OAuth 2.0 legacy webhooks, `201` is required, but for HMAC/API Key `200` or `201` is standard)*.<br>  2. JSON body with `"success": true` (`{"success": true}`).<br>  3. Completed within **30 seconds** (connect timeout `15 s`, total timeout `30 s`).<br>- **Critical rule in `docs.sepay.vn/tich-hop-webhooks.html`:** *"Endpoint trả 200 nhưng thiếu `{"success": true}` chỉ bị ghi là thất bại, không được gọi lại."* (Returning HTTP `200` without `{"success": true}` is logged as failed by SePay and **will NOT be auto-retried**!) | **Matches Spec 11 — enforce strict status code discipline:**<br>1. Always serialize `{"success": true}` with HTTP `200` for processed, duplicate, or ignored events.<br>2. Never return HTTP `200` with `{"success": false}` on transient errors; always return HTTP `500` on transient failures so SePay's Fibonacci retry triggers (`HTTP status outside 200–299`). |
| **d) Retry Schedule, Conditions & Ordering** | **§5.8, §7:**<br>- 8 deliveries (1 initial + 7 retries) over ~33 minutes when auto-retry is enabled.<br>- Outages longer than retry window are recovered by `ReconciliationService`. | **`/vi/sepay-webhooks/xu-ly-loi` & `/bao-mat`:**<br>- **Conditions:** Retries when *"Tự động gửi lại khi server trả lỗi"* is enabled AND either (1) connection fails (DNS, connection refused, timeout > 30s, SSL/CA error) OR (2) HTTP status is outside `200–299`.<br>- **Schedule (Fibonacci):**<br>  - Attempt 1: immediate (`0 min`)<br>  - Attempt 2: +`1 min` (total `1 min`)<br>  - Attempt 3: +`1 min` (total `2 min`)<br>  - Attempt 4: +`2 min` (total `4 min`)<br>  - Attempt 5: +`3 min` (total `7 min`)<br>  - Attempt 6: +`5 min` (total `12 min`)<br>  - Attempt 7: +`8 min` (total `20 min`)<br>  - Attempt 8: +`13 min` (total `33 min`)<br>- **Safety cutoff:** Webhooks older than **5 hours** are never picked up by the retry cron.<br>- **Manual replay:** Admins can manually replay any log (even succeeded ones) from Dashboard (rate-limited to 10 replays/min/company in Test mode).<br>- **Ordering:** SePay explicitly states webhook delivery order is **not guaranteed** (*"Hai giao dịch cách nhau vài giây có thể đến endpoint theo thứ tự đảo ngược nếu webhook cũ đang retry"*).<br>- **Payment code structure (`cau-hinh-ma-thanh-toan`):** Prefix is `2–5` chars (`GH` = 2 chars, valid), but **default suffix length is `6–8` chars** (configurable up to `30`). | **Matches Spec 11, with 2 operational requirements to document:**<br>1. Because SePay does not guarantee webhook ordering and allows manual replay of already-succeeded logs, Spec 11's inbox deduplication (`UNIQUE(Provider, ProviderTransactionId)`) and state-machine guards are essential.<br>2. **Important Dashboard Precondition (§2.2):** Because GroceryHub payment codes are `GH` + **10 digits** (`GH1000000001`), the user **must** change *"Độ dài hậu tố tối đa"* in **Cấu hình Công ty → Cấu hình chung → Cấu trúc mã thanh toán** from the default `8` to `10` (e.g., Min `10`, Max `10`, type `Số nguyên`), otherwise SePay will either truncate or fail to extract `code`! |

## 4. Summary of Actionable Adjustments for Phase 10 Implementation

1. **Webhook Authentication (`Hmac` + `ApiKey`):** Keep Spec 11 §5.2 as designed (`Hmac` primary verifying `X-SePay-Timestamp` within ±300s and `X-SePay-Signature: sha256=<hex>` over `"{timestamp}.{rawBody}"`, plus `ApiKey` fallback verifying `Authorization: Apikey <key>` in constant time). Both are confirmed native SePay webhook modes.
2. **Webhook Payload DTO Nullability:** Ensure `SubAccount`, `Code`, `Description`, and `ReferenceCode` are nullable `string?` in C#, and treat both `null` and `""` on `Code` as absent so the regex fallback (`GH\d{10}` over `Content`) always runs when `Code` is empty.
3. **Payment Code Suffix Length in SePay Dashboard:** Emphasize in user setup notes (`docs/spec/11` §2.2) that in **Cấu hình Công ty → Cấu hình chung → Cấu trúc mã thanh toán**, for prefix `GH`, the user **must** set **Độ dài hậu tố tối thiểu = 10** and **Độ dài hậu tố tối đa = 10** (changing away from SePay's default `6–8`) so 10-digit codes (`GH1000000001`) are extracted into `code`.
4. **Reconciliation Service (API v2 vs. v1 & Deduplication):**
   - Support SePay API v2 (`GET https://userapi.sepay.vn/v2/transactions` for Production, `GET https://userapi-sandbox.sepay.vn/v2/transactions` for Sandbox) with `Authorization: Bearer <SEPAY_API_TOKEN>`, pagination (`page`, `per_page=100`), and rate-limit handling (`3 req/s`, HTTP `429` `Retry-After`).
   - Normalize API v2 fields (`bank_brand_name` → `gateway`, `transaction_date` → `transactionDate`, `account_number` → `accountNumber`, `va` → `subAccount`, `amount_in`/`amount_out` + `transfer_type` → `transferAmount`/`transferType`, `transaction_content` → `content`, `reference_number` → `referenceCode`).
   - Because API v2 uses a UUID `id` whereas webhooks use a numeric integer `id`, `ReconciliationService` **must** check both `WebhookEvents.ProviderTransactionId == tx.Id` AND existing `PaymentTransactions` / matched `PaymentAttempts` (by `ReferenceCode == tx.ReferenceNumber` + `AccountNumber` + `TransferAmount`, or `PaymentCode` already `Paid`) before processing a transaction as a missed webhook.
5. **Sandbox Setup Instructions:** Direct the user to the built-in **Test mode** switch in the left sidebar of `https://my.sepay.vn` (instead of the defunct `my.dev.sepay.vn` domain).
